# 优惠券体系统一设计

## 动机

当前系统有三套独立的优惠机制，管理分散、数据分散：

| 机制 | 存储位置 | 发放方式 | 管理入口 |
|------|----------|----------|----------|
| 普通优惠券 (type=0) | `litemall_coupon` 表 | 用户领取 / 首页弹窗 | 优惠券管理页 |
| 特殊券 (type=1~4) | `litemall_coupon` 表 | 各自专用渠道 | 优惠券管理页 |
| 首单优惠 | `litemall_system` KV 表 | 下单时直接立减 | 系统配置（Vue 后台） |

问题：
- 首单优惠不是券，走独立立减逻辑，管理入口分散
- type=1（注册券）和 type=3（新人券）无自动发放逻辑，创建了也用不了
- 优惠券管理和系统配置两个入口管优惠券相关的事，老板认知成本高

## 方案：优惠券管理作为唯一入口

所有优惠券都在"优惠券管理"里创建和管理，系统配置页只保留生日券的开关和参数。

### 统一后的类型体系

| type | 名称 | 发放方式 | 首单限制 |
|------|------|----------|----------|
| 0 | 通用券 | 用户主动领取 / 弹窗领取 | 无 |
| 1 | 新人券 | 注册时自动发放 | 仅首单可用 |
| 2 | 兑换券 | 兑换码兑换 | 无 |
| 3 | *(保留，不在 UI 显示)* | — | — |
| 4 | 生日券 | 定时任务自动发放 | 无 |

**type=1 新人券**：合并原 type=1（注册券）和 type=3（新人券），注册时自动发放到用户账户，下单时校验首单。

### 自动发放逻辑

**注册自动发券（type=1）**：
- 触发点：`wx-auth` 云函数注册成功后
- 逻辑：查找 `status=0 AND type=1` 的券模板，写入 `litemall_coupon_user`
- 首单校验：下单选券时，type=1 的券仅在用户无已完成订单时可用
- 如果存在多张 type=1 的券，全部发放

**生日自动发券（type=4）**：
- 不变，`task-coupon` 定时任务每天查过生日用户发放
- 系统配置页保留：开关 + 关联券ID + 有效天数

**弹窗发券（type=0 + popup=1）**：
- 不变，首页弹窗领取
- couponEdit 页面新增 popup 开关（仅 type=0 时显示）

### 系统配置页调整

- **删除**：首单优惠金额配置（`litemall_newuser_first_order_discount`）
- **保留**：生日券配置
  - 开关（`litemall_birthday_coupon_coupon_status`）
  - 关联优惠券（`litemall_birthday_coupon_id`）— 下拉选 type=4 的券
  - 有效天数（`litemall_birthday_coupon_days`）

### 弹窗推荐（popup）开关

- 位置：couponEdit 页面，type=0 时显示"弹窗推荐"开关
- 存储：`litemall_coupon.popup` 字段（TINYINT, 0/1）
- 作用：首页弹窗查询 `popup=1` 的通用券推荐给用户

## 改动范围

### 前端（小程序管理端）

| 页面 | 改动 |
|------|------|
| couponManage | Tab 筛选改为：全部/通用/新人/兑换/生日（移除原"注册"，"新人"对应 type=1） |
| couponEdit | 类型选项改为：通用领券/新人券/兑换码/生日专属；type=0 时显示 popup 开关 |
| systemConfig | 移除首单优惠配置，保留生日券开关+关联券选择+有效天数 |

### 云函数

| 云函数 | 改动 |
|--------|------|
| wx-auth | 注册成功后自动发放 type=1 的券 |
| wx-coupon | receive 接口不变（只允许 type=0）；选券时 type=1 校验首单 |
| wx-cart | 移除首单立减逻辑（`newuserDiscount`） |
| wx-order | 移除首单立减逻辑（`newuserDiscount`） |
| wx-manager-marketing | 券列表/创建/编辑适配新类型体系；新增 popup 字段的读写 |

### 数据库

- 不改表结构
- type=3 从 UI 入口移除，数据库字段保留（避免迁移风险）
- 首单立减的 KV 配置不再使用，但不删除（兼容性）

### 不需要数据迁移

确认线上无用户使用首单优惠，直接切换即可。

## 风险点

1. **type=1 券的发放时机**：如果注册时没有 type=1 的券（老板还没创建），用户注册后不会收到券。这是预期行为 — 老板需要先创建新人券。
2. **多张 type=1 券**：如果存在多张 type=1 的券，注册时全部发放。需要确认是否合理。
3. **已存在的 type=3 数据**：如果数据库中已有 type=3 的券记录，它们不会在管理端显示。可通过数据库手动处理。
